# Installing savestate

- [`crds/`](crds) holds the CustomResourceDefinitions for `Sandbox`, `Checkpoint` and
  `Transfer`, generated by `savestate crds` (CI checks they are current).
- [`base/`](base) is a kustomize base with placeholder values: the `savestate-system`
  namespace, the controller Deployment, the node-agent DaemonSet, RBAC for each, the
  installation config as a ConfigMap, and one example sandbox namespace,
  `sandboxes`.

Nodes that run VMs need KVM, `/dev/net/tun`, `/dev/vhost-vsock` (the node agent's
`load-modules` init container runs `modprobe vhost_vsock` where it is missing, from
the host's `/lib/modules`), and a disk for `stateDir`. VM pods are never privileged: the node
agent hands them those devices as a kubelet device plugin. Their launcher container
runs as root with only `NET_ADMIN`, `CHOWN`, `SETUID`, `SETGID` and `KILL`, no privilege
escalation, a read-only root filesystem and the seccomp profile
`savestate/vm.json` (the container runtime's default plus `AF_VSOCK` sockets), and
drops to uid 65532 before starting QEMU, which applies its own seccomp filter.
Install in this order:

1. Label the VM nodes (the base selects `savestate.dev/node: "true"`), or set your own
   selection (`vm.nodeSelector` or `vm.nodeAffinity`) in the config and `base/node.yaml`.
2. Write `config.yaml` for your installation (see below and
   [`base/config.yaml`](base/config.yaml)).
3. Apply an overlay of your own that replaces every placeholder (it includes the
   CRDs from `crds/`): `kubectl apply -k <overlay>`.
4. Wait for `deployment/savestate-controller` and `daemonset/savestate-node` in
   `savestate-system` to roll out. A node-agent pod stuck in `Init` on a node means
   that node cannot run `vm.cpuModel`: its `probe-cpu` container's termination
   message lists the missing CPU features.
5. Publish a base image (below), or use the generic one, `ghcr.io/samcm/savestate-base`
   (`:main` from every push to main; pin it by digest), and create a sandbox from it:
   `savestate create web-1 --image <registry>/<repo>@sha256:<digest> --vcpus 2 --memory 4Gi --disk 30Gi --namespace <namespace>`.

The overlay:

```yaml
# kustomization.yaml in your overlay
resources:
  - https://github.com/samcm/savestate//deploy/base?ref=<commit>
images:
  - name: ghcr.io/samcm/savestate
    digest: sha256:<digest>
configMapGenerator:
  - name: savestate-config
    namespace: savestate-system
    behavior: replace
    files:
      - config.yaml
```

A sandbox image is a container image whose filesystem holds `/rootfs.qcow2`, the
guest disk (see [guest/README.md](../guest/README.md)); the node agent pulls it by
digest and caches the disk per node:

```dockerfile
FROM scratch
COPY rootfs.qcow2 /rootfs.qcow2
```

Kubernetes 1.32 to 1.37 is supported (CI tests 1.32 and 1.37). The controller
serves Prometheus metrics on port 9090 at `/metrics`.

## What your installation supplies

The repository holds behaviour, schemas, generic defaults and placeholder examples.
Everything below describes one installation and comes from your overlay; nothing in
`base/` is a real cluster's value.

| What | Where |
| --- | --- |
| Image, pinned by digest | kustomize `images:`. Checkpoints restore only on the image they were taken with. |
| Sandbox namespaces | `namespaces` in the config, and one copy of [`base/sandboxes.yaml`](base/sandboxes.yaml) per namespace (Namespace with the privileged Pod Security level, RoleBindings for the controller and node agent, a NetworkPolicy refusing ingress to VM pods except the ports sandboxes expose). |
| Who may use sandboxes | RoleBindings of the `savestate-user` ClusterRole in sandbox namespaces. Do not give them pod creation there. |
| Quotas | ResourceQuotas in sandbox namespaces. A VM pod requests its sandbox's memory plus `vm.memoryOverhead`, so memory quotas count sandboxes directly. |
| Which nodes run VMs, tolerations | `vm.nodeSelector`, `vm.nodeAffinity` (e.g. a list of hostnames, without labelling nodes) and `vm.tolerations` in the config, and the same selection on the node-agent DaemonSet ([`base/node.yaml`](base/node.yaml)). The base selects nodes labelled `savestate.dev/node: "true"`. |
| Guest CPU model | `vm.cpuModel` (required). `host` where all VM nodes are one machine type: guests get the node's CPU, and a checkpoint restores only on nodes with an identical CPU (the node agent labels nodes `savestate.dev/cpu`). A named QEMU model every VM node can run (e.g. `EPYC-Rome-v4`) is run with `enforce`, checked on every node at start-up (a node that cannot run it shows the missing features in its node-agent pod's `probe-cpu` init container), and lets checkpoints move between any VM nodes. |
| VM shapes offered | `vm.shapes` (default: any shape). |
| CPU each VM reserves | `cpuRequest` per shape, else `vm.cpuRequestPerVcpu` per vCPU (default `1`, a whole CPU per vCPU: the pod's CPU limit equals its request and it is Guaranteed). Reserve less to fit VMs on nodes that keep some CPU for themselves, e.g. `cpuRequest: 3500m` for a 4-vCPU shape on 4-CPU nodes; such pods have no CPU limit and are Burstable (see "CPU requests below the vCPU count" in [docs/design.md](../docs/design.md)). Memory is always request = limit. |
| Memory files and the page cache | `vm.memoryFileDirectIo` (default `false`): write and read checkpoint memory files with O_DIRECT. Through the page cache a save usually pauses for less, and concurrent restores of one checkpoint share the cached file. |
| Memory overhead margin | `vm.memoryOverhead` (default `512Mi`); measure QEMU's overhead on your nodes. |
| VMs per node | `vm.slotsPerNode` (default `110`, the kubelet's default pod limit). The node agent is a kubelet device plugin: it advertises that many units of `savestate.dev/vm`, each VM pod takes one, and with it the kubelet hands the pod `/dev/kvm`, `/dev/net/tun` and `/dev/vhost-vsock`. Set it lower to cap VMs per node; CPU and memory requests limit them otherwise. |
| Kubelet directory | `kubeletDir` (default `/var/lib/kubelet`, also k3s's) and the node agent's `device-plugins` and `seccomp` `hostPath`s in [`base/node.yaml`](base/node.yaml) must agree. The node agent installs the VM pods' seccomp profile as `seccomp/savestate/vm.json` there at start-up, before it advertises any VM slot. |
| Base images, registries, pull credentials | `images.registries`, and `images.auth` pointing at a Docker `config.json` you mount into the node agent (for example from a Secret, by patching `base/node.yaml`); `images.plainHttp` for registries reached without TLS; `images.prefetch` for images every node pulls when its agent starts. |
| Egress allowlist, DNS | `network.egressAllow` and `network.dns`. Guests reach the internet; cluster, node, link-local and private ranges are dropped except what you allow. |
| Who reaches exposed ports | `network.exposeFrom`: NetworkPolicy sources (namespace and pod selectors, IP blocks) allowed to connect to the ports sandboxes expose (`spec.ports`). Default: pods in the sandbox's own namespace. Your CNI must enforce NetworkPolicies; the launcher forwards only exposed ports either way. |
| External exposure | Your choice of Ingress or `LoadBalancer`; see [Exposing a sandbox outside the cluster](#exposing-a-sandbox-outside-the-cluster). |
| State directory | `stateDir` (default `/var/lib/savestate`) and the node agent's `hostPath` must agree, on a disk large enough for your checkpoints. |
| Object stores | `stores`: per store an S3-compatible `endpoint`, `bucket`, `region`, `prefix` (one prefix per installation) and `credentialsSecret`, a Secret in `savestate-system` with `accessKeyId` and `secretAccessKey`. `export` names the store every checkpoint is exported to (default: only checkpoints with `spec.export`). Without stores, checkpoints live only on the node that took them. |
| Cache eviction | `cache.minFreePercent` (default 25): below that much free space on the state directory's filesystem, nodes drop their copies of exported checkpoints. |
| Disk guard | `vm.minFreeDiskPercent` (default 20): below that much free space, a node takes no new VMs (status taint `status-taint.cluster-autoscaler.kubernetes.io/savestate-disk`). Keep it above the kubelet's `imagefs.available` eviction threshold. |
| TTL limits, transfer concurrency | `ttl` and `transfers.perNode` (defaults: no limits, four transfers per node; each buffers up to 256 MiB in the node agent, whose memory limit in `base/node.yaml` allows four). |

[`base/config.yaml`](base/config.yaml) is the example config; every field is
documented there and in `crates/savestate-api/src/config.rs`. Fields not set take
their defaults; a missing required field or an unknown field stops the controller
and node agent with an error naming it.

## Exposing a sandbox outside the cluster

A sandbox with `spec.ports` and `spec.service: true` has a `ClusterIP` Service named
after it. Reaching it from outside the cluster is up to the installation. For
example, with an ingress controller running in the namespace `ingress`, let it
through in the config:

```yaml
network:
  exposeFrom:
    - namespaceSelector:
        matchLabels: {kubernetes.io/metadata.name: ingress}
```

and route a host to the sandbox's Service:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-1
  namespace: sandboxes
spec:
  rules:
    - host: web-1.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-1          # the sandbox's Service
                port: {number: 8080}
```

A `LoadBalancer` Service of your own works the same way: select the VM pod with
`savestate.dev/sandbox-uid: <the sandbox's UID>` and add the load balancer's
source ranges (or `0.0.0.0/0`) to `exposeFrom` as an `ipBlock`. Each fork of a
sandbox is its own sandbox, with its own pod and Service, so route to each one
separately.

## Running on an autoscaled cluster

savestate works with the upstream Kubernetes cluster autoscaler: pending VM pods add
nodes, and nodes without VMs and without the only copy of a checkpoint are removed.

**What the autoscaler must honour.** Upstream defaults do all of this; check that a
managed autoscaler does too.

- `cluster-autoscaler.kubernetes.io/safe-to-evict: "false"` on VM pods: evicting
  one destroys its VM, so a node running any VM is never scaled down. VM pods also
  mount `hostPath` volumes, which `--skip-nodes-with-local-storage` (default `true`)
  treats the same way. Node-agent pods are DaemonSet pods and never block. Keep any
  other non-DaemonSet pod you add to `savestate-system` off `hostPath` and disk
  `emptyDir`s, or it will hold its node.
- `cluster-autoscaler.kubernetes.io/scale-down-disabled: "true"` on nodes: the node
  agent sets it while its node holds a `Ready` checkpoint no store has, and removes it
  once every local checkpoint is in a store or gone. Set `export` so that lasts only
  as long as an export takes.
- Startup taints (prefix `startup-taint.cluster-autoscaler.kubernetes.io/`), if you
  use the one below, and status taints (prefix
  `status-taint.cluster-autoscaler.kubernetes.io/`): the node agent sets one while
  its node is short of disk.

**At least one node per VM pool.** VM pods request `savestate.dev/vm`, the node
agent's device-plugin resource. To decide whether a new node would fit a pending
pod, the autoscaler copies a node already in the pool, which carries the resource.
From zero nodes it asks the cloud provider for a template instead, and templates that
hold only CPU, memory, pods, labels and taints lack the resource, so no pod that
needs it triggers a scale-up. Keep the pool's minimum at 1. (The autoscaler caches
the last real node of a group, so scale-up from zero can work until the autoscaler
restarts; do not rely on it.) Where your provider takes node-template hints for
extended resources and labels, advertise `savestate.dev/vm: <vm.slotsPerNode>`
and, with a named CPU model, the label `savestate.dev/cpu: <first 16 hex digits of
sha256(vm.cpuModel)>` (`printf %s EPYC-Rome-v4 | sha256sum | cut -c1-16`), and a
pool can start at zero. The same holds for disk: VM pods request
`ephemeral-storage`, which templates without it lack too. CDI does not remove the need: Kubernetes hands a container
CDI devices only through a device plugin's allocation or through DRA, and both are
node resources a template must carry.

**Export by default.** Set `stores` and `export`. A checkpoint is then in a store
seconds after it is `Ready` (the upload, plus the time a running store garbage
collection still needs, usually none), after which:

- its node is free to be scaled down once its VMs are gone;
- a sandbox from it may start on any node whose guests get the checkpoint's CPU
  (`savestate.dev/cpu`), not only on the nodes holding it. Nodes holding it are
  preferred; when none has room the pod stays `Pending`, the autoscaler adds a node,
  the controller imports the checkpoint there (`WaitingForTransfer`), and the VM
  restores. A pod created before the export finished, pinned to the holders, is
  replaced once the export lands (event `Replaced`).

A sandbox from a checkpoint that lands on a new node takes about: autoscaler
reaction (its scan interval, 10 s by default, plus the provider's response) + node
boot and join + node-agent start (pulling the savestate image, the CPU probe) +
import + restore. On one managed cluster with 64 GiB nodes that was 163 s from
`Pending` to `Running`: the autoscaler asked for a node after 61 s and the node was
Ready 139 s after the pod went pending; the import of 467 MiB took 4.5 s and the
restore 3.3 s. Node boot dominates; the import grows with the checkpoint's memory
file and disk layers. Stores do not hold base images: a node that lacks one pulls it
from its registry (or has it from `images.prefetch`) while the layers download, so
keep every image a checkpoint may still need in its registry.

**CPU model.** Use a named `vm.cpuModel` that every machine type the pool may get
runs (for example `EPYC-Rome-v4` across Zen 2 and Zen 3, or a `Skylake-Server`
variant on Intel; check with the node agent's `probe-cpu` container on each). With
`host`, a checkpoint restores only on nodes with an identical CPU, so a new node of
another CPU generation cannot take a fork. With a named model every node that passes
the probe gets the same `savestate.dev/cpu` label, and any of them can import any
checkpoint.

**CPU requests.** Memory is never overcommitted, so on memory-sized nodes memory
should decide how many VMs fit. Set each shape's `cpuRequest` (or
`vm.cpuRequestPerVcpu`) so CPU does not bind first: at most the node's allocatable
CPU divided by the number of VMs its allocatable memory holds. On a node with 8 CPUs
and 64 GiB (about 7.9 CPUs and 60 GiB allocatable) six 8 GiB VMs fit by memory
(8 GiB + `vm.memoryOverhead` each), so request at most 1.3 CPUs per VM, whatever
its vCPU count; whole CPUs per vCPU would fit one 4-vCPU VM. VMs then share the
node's CPU (see "CPU requests below the vCPU count" in
[docs/design.md](../docs/design.md)).

**Node size.** A node is removed only once its last VM is gone, so smaller nodes
empty sooner and larger ones pack better. Size nodes to hold a handful of your
common shape (for 8 GiB VMs, 32–64 GiB nodes hold 3–7) and leave headroom for the
node's reserved memory, which grows with node size. VM pods prefer nodes that
already run VMs, so new VMs fill busy nodes first and idle ones drain. Give each
node's `stateDir` disk room for the base images, the layers of its sandboxes and the
memory files of its local checkpoints (about each guest's used RAM); exported copies
are dropped first when it fills (`cache.minFreePercent`).

**Faster node join.**

- `images.prefetch`: the base images your sandboxes boot from, by digest. Each new
  node pulls them as soon as its agent starts, so the first boot or import there does
  not wait for a multi-GiB pull. The node takes VMs meanwhile; only a boot or import
  needing an image still being pulled waits for it.
- A startup taint `startup-taint.cluster-autoscaler.kubernetes.io/savestate=true:NoSchedule`
  on the VM pool (applied when a node registers). The node agent removes it once its
  node advertises VM slots, and again whenever it reappears, for example when an
  edit of the pool copies the pool's taints onto existing nodes. Until then the
  autoscaler counts the node as still starting. Without the taint there are a few
  seconds (14 s in one measurement) in which the autoscaler sees a Ready node the
  pending VM pods cannot use yet; with many pods pending it may add another node,
  which it removes again after its scale-down delay. Use this prefix rather than a
  taint of your own: the autoscaler leaves startup taints out of the node templates
  it copies from existing nodes, while any other taint on them keeps it from
  scaling the pool for pods that do not tolerate it.

An autoscaled installation's config, beyond the basics above:

```yaml
vm:
  cpuModel: EPYC-Rome-v4            # a named model every node type in the pool runs
  shapes:
    - {vcpus: 4, memory: 8Gi, disk: 60Gi, cpuRequest: 1300m}
  nodeSelector:
    savestate.dev/node: "true"
images:
  prefetch: [ghcr.io/example/base@sha256:...]
stores:
  archive:
    endpoint: https://s3.example.com
    bucket: example-checkpoints
    region: example-region-1
    prefix: savestate
    credentialsSecret: savestate-store-archive
export: archive
```

and a VM pool with a minimum of one node, the label `savestate.dev/node=true` and,
where it applies, the startup taint.
